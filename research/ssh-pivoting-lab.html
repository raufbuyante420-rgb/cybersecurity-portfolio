01 Introduction & Lab Objective

I initially began studying network pivoting as part of my preparation and practical training for the CRTA certification. To practice these concepts in a controlled environment, I created a home lab demonstrating SSH-based routing and network pivoting across segmented networks.

The lab was built in VirtualBox using:

Kali Linux

Role: Attacker

Network: KALI-NET (External)

IP: 192.168.56.10

Ubuntu Server

Role: Pivot Host

Network: KALI-NET + Internal

IPs: 192.168.56.20 / 10.10.10.20

Metasploitable 2

Role: Internal Target

Network: Internal (Isolated)

IP: 10.10.10.30

The Objective:
Establish an SSH connection from Kali Linux to Ubuntu, then use that connection as a pivot into the internal network. Kali Linux does not have direct access to Metasploitable 2 — Ubuntu serves as the intermediary between the external KALI-NET network and the isolated internal network.

02 Network & Adapter Configuration

I used VirtualBox for this lab and enabled network adapters attached to INTERNAL networks. This creates an isolated network segment where the external network (KALI-NET) is separated from the internal network that contains the target.

Kali Linux Configuration

For the Kali machine, I configured KALI-NET as the external network interface. I also added a second network adapter set to NAT to provide internet access to the attacker machine for installing tools and updates.

Ubuntu Server Configuration

The Ubuntu Server is configured with connectivity to both the external and internal networks. This dual-network configuration allows Ubuntu to function as the pivot host — receiving traffic from Kali on the external interface and forwarding it to the internal network.

03 Static IP Addressing

After configuring the virtual network adapters, I assigned static IP addresses to each machine. The resulting addressing scheme is:

Machine Interface IP Address Network
Kali Linux eth0 192.168.56.10 KALI-NET
Ubuntu Pivot (External) enp0s3 192.168.56.20 KALI-NET
Ubuntu Pivot (Internal) enp0s8 10.10.10.20 Internal
Metasploitable 2 eth0 10.10.10.30 Internal

Since those OS installations don't have IP addresses assigned yet, I used the following commands to set static IPs based on the external network configuration:

Kali Linux — 192.168.56.10

Kali Terminal 
sudo ip addr flush dev eth0 && sudo ip addr add 192.168.56.10/24 dev eth0 && sudo ip link set eth0 up

Ubuntu Pivot — External (192.168.56.20)

Ubuntu Terminal 
sudo ip addr flush dev enp0s3 && sudo ip addr add 192.168.56.20/24 dev enp0s3 && sudo ip link set enp0s3 up

Ubuntu Pivot — Internal (10.10.10.20)

Ubuntu Terminal 
sudo ip addr flush dev enp0s8 && sudo ip addr add 10.10.10.20/24 dev enp0s8 && sudo ip link set enp0s8 up

Metasploitable 2 — 10.10.10.30

Metasploitable Terminal 
sudo ifconfig eth0 10.10.10.30 netmask 255.255.255.0 up
After that, all machines should have the correct IP addresses, and we can verify the configuration before moving to connectivity testing.

04 Connectivity Testing

With the network configuration complete, I tested connectivity between the machines. Kali Linux should be able to reach Ubuntu because both systems are connected to the external network.

However, Kali Linux should NOT be able to directly reach Metasploitable 2 because the target resides on the isolated internal network. This behavior establishes the baseline condition that the pivot is intended to overcome.

Note: Kali should not be able to ping Metasploitable 2 because it is inside the internal network. However, when we ping Ubuntu — which is on the KALI-NET network — the ping will succeed.

05 Establishing the SSH Pivot

After confirming the network configuration, I established an SSH connection from Kali Linux to the Ubuntu pivot host. Once we have the credentials for the Ubuntu SSH server, we can connect to it from the Kali machine.

The SSH Command

Kali Terminal 
ssh -D 9050 pivot@192.168.56.20
The important option is -D 9050. This creates a SOCKS proxy on Kali at 127.0.0.1:9050. SSH dynamic forwarding allows applications using the SOCKS proxy to request TCP connections through the SSH server.

Now we have an active SSH terminal on the Ubuntu machine. Back on our Kali machine, we need to set up ProxyChains to route our network traffic through the SSH SOCKS proxy.

06 ProxyChains Configuration

The SSH session creates a SOCKS proxy on Kali Linux. I then configured ProxyChains to use this local SOCKS5 proxy so that supported applications can send traffic through the SSH connection.

The ProxyChains configuration file is located at /etc/proxychains4.conf. We need to add the following entry at the end of the configuration:

/etc/proxychains4.conf 
# Add at the end of the file
socks5 127.0.0.1 9050

Using tail we can verify the entry has been added to the configuration file.

Now we have successfully established an active SSH terminal and configured ProxyChains. Time to test if the pivot works!

07 Testing the Pivot

After configuring ProxyChains, I tested whether Kali Linux could reach the internal Metasploitable 2 host through the Ubuntu pivot. I used Netcat through ProxyChains to test TCP connectivity to port 22 on the internal target:

Kali Terminal 
proxychains4 nc -vz -w 5 10.10.10.30 22

The successful result demonstrates that traffic from Kali Linux can traverse the SSH SOCKS proxy and reach the internal network.

We can see that it's now working! We can also try to curl using proxychains to further verify internal network access.

Now we have access to the internal network using our Kali Linux, with Ubuntu as the pivot machine. Then we can even SSH into Metasploitable 2 from Kali using proxychains!

08 Internal Network Access & Conclusion

The final step is establishing SSH connectivity to Metasploitable 2 through ProxyChains and the SSH pivot. Since Metasploitable 2 runs an older version of SSH, the command must use legacy-compatible options.

Conclusion

With the pivot operational, Kali Linux can access services on the internal network through Ubuntu. This lab demonstrates the practical use of:

  • SSH Dynamic Port Forwarding (-D flag) to create a SOCKS proxy
  • SOCKS5 Proxy tunneling at 127.0.0.1:9050
  • ProxyChains to route application traffic through the SSH tunnel
  • Network Pivoting to reach a network segment not directly accessible from the attacker machine

Key Takeaways

  1. SSH -D creates a local SOCKS proxy that forwards TCP through the SSH server
  2. ProxyChains wraps applications so they use the SOCKS proxy transparently
  3. Separating networks with a dual-homed host enables controlled pivoting
  4. This technique is essential for penetration testers moving laterally in segmented environments
